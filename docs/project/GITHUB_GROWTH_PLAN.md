# Anunnaki Growth Plan

Anunnaki’s strongest position is complementary: Microsoft MarkItDown is the powerful conversion engine; Anunnaki is the approachable Windows desktop workflow around it. Growth should communicate that distinction accurately and never imply Microsoft endorsement.

## GitHub SEO strategy

Use the repository description: “Local Windows desktop GUI for Microsoft MarkItDown—batch-convert documents to Markdown without a CLI.” Use focused topics: `markitdown`, `markdown`, `document-converter`, `file-converter`, `python`, `pyside6`, `windows`, `desktop-app`, `pdf-to-markdown`, `docx-to-markdown`, `xlsx-to-markdown`, `pptx-to-markdown`, `open-source`.

## README strategy

Keep the opening value proposition and attribution visible. Add real screenshots of the drop area, queue, conflict dialog, and completed conversion state. Keep installation to one short Windows path and one source path.

## Screenshots strategy

Capture only synthetic, non-sensitive documents. Use consistent dark-theme screenshots at 1440×900 and show the Anunnaki logo, drag-and-drop workflow, batch queue, and safe overwrite options.

## Demo video strategy

Create a 60–90 second screen recording: launch the app, drop a synthetic PDF/DOCX/CSV set, retain the default same-folder output setting, convert, show the generated Markdown, and mention that MarkItDown is the engine.

## Release strategy

Publish versioned Windows ZIP assets that contain the entire `Anunnaki` folder. Include a concise changelog, checksum, supported-platform note, known limitations, and explicit upstream attribution.

## Reddit strategy

Share only where self-promotion is welcome and provide value first: relevant Python, Markdown, note-taking, and local-first productivity communities. Ask for focused feedback; do not repost or use vote manipulation.

## LinkedIn launch strategy

Publish a short build story focused on the practical problem—turning office files into Markdown without a terminal—then credit Microsoft MarkItDown and show a short demo GIF.

## DEV.to article idea

“Building a local-first Windows GUI around Microsoft MarkItDown.” Cover architecture, background workers, output safety, packaging lessons, and attribution.

## Hacker News suitability

Suitable only after a polished release with source, clear differentiation, reproducible build instructions, and a concise technical write-up. Submit once; engage honestly with technical feedback.

## GitHub Discussions strategy

Enable Discussions after the first release. Start categories for Questions, Ideas, Show and Tell, and Upstream compatibility. Summarize resolved recurring questions in documentation.

## Good First Issue strategy

Label small, scoped tasks with reproduction steps and expected outcomes: accessibility labels, file-type help text, test coverage, and documentation screenshots.

## 30-Day Launch Plan

| Period | Focus |
| --- | --- |
| Days 1–3 | Publish source, first release ZIP, screenshots, and a short demo. |
| Days 4–10 | Collect issue reports, verify installation guidance, and fix onboarding friction. |
| Days 11–20 | Publish one technical article and invite targeted feedback in appropriate communities. |
| Days 21–30 | Ship a small maintenance release, label good first issues, and open Discussions. |

Never use fake stars, automated engagement, spam, bots, or misleading claims.
